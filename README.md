# GitHub PR Review Toolkit

One Tampermonkey userscript that adds a floating panel and a few per-file helpers to GitHub pull requests. It needs no token: it reads GitHub through your already signed-in browser session.

## Install

1. Install Tampermonkey.
2. Open [gh-pr-review-toolkit.user.js](https://raw.githubusercontent.com/waterfausett/gh-toolkit/master/gh-pr-review-toolkit.user.js) and click **Install**. The optional [Actions workflow filter](https://raw.githubusercontent.com/waterfausett/gh-toolkit/master/gh-actions-workflow-filter.user.js) installs the same way.
3. Open a PR. Tampermonkey will ask to allow connections to `github.com`, `raw.githubusercontent.com` and `patch-diff.githubusercontent.com`; allow them.

### Updates

Installed scripts update themselves from this repo through `@updateURL`. Tampermonkey checks on its own schedule (Settings → Script Update), or immediately from Dashboard → "Check for userscript updates". It only updates when `@version` increases, so bump it with every change you push. Config is kept in Tampermonkey storage and survives updates. Edits made in the Tampermonkey editor are overwritten by the next update, so make changes in the repo.

## First-time setup

Set `myOwners` to the CODEOWNERS teams you belong to, or files owned by your teams will be marked as owned by others. Your own GitHub login is picked up automatically, so only teams need listing. Open the Tampermonkey menu, choose **Edit config (JSON)**, and edit the array, for example `"myOwners": ["my-org/my-team"]`. Use the same `org/team` form that appears in CODEOWNERS. The panel can't look up your memberships itself because that needs a GitHub API token.

If the Linear and ADO ticket chips don't link as expected, see `ticketRules` and `adoBase` in the same config.

## How data is loaded

Up to three requests per PR, made by Tampermonkey with your GitHub session cookies:

- `/<owner>/<repo>/pull/<n>.diff` for the file list, per-file additions and deletions, and blob SHAs (from the diff's `index` lines). The same pass flags whitespace-only and rename-only files, scans added lines for debug leftovers and reads dependency manifests; only those results are kept, not the diff text.
- `/<owner>/<repo>/raw/HEAD/.github/CODEOWNERS` (falling back to `CODEOWNERS` and `docs/CODEOWNERS`) for ownership.
- `/<owner>/<repo>/pull/<n>/commits` with `Accept: application/json` for the PR's commit list and head SHA (only while "New commits since your last look" is on). This is roughly 2 KB per commit.

If one fails (signed out, SSO expired, very large PR where GitHub refuses to render the diff), the panel says so and the features that depend on it switch off. Everything that only reads the page keeps working.

## Features

| Feature | Notes |
|---|---|
| Always-visible tab nav | Conversation / Commits / Checks / Files in the panel, Alt+1..4. By default **Checks ↓** scrolls to the merge box's checks summary on the Conversation tab (going there first if you're on another tab); turn on "Checks nav item opens the Checks tab" in settings to open the tab instead. The title bar also has a ↑ Top button that stays put when the panel is collapsed. Handles both `/files` and `/changes`. Plain clicks navigate in-page by clicking a real link so GitHub's own router handles it; if the URL hasn't changed after 1.5s the script falls back to a full page load. |
| Review button | **Review** in the panel bar, or Alt+R. Clicks GitHub's own "Review changes" / "Submit review" button so its review dialog opens; it never submits anything. From another tab it goes to Files first and waits up to 10s for the button to render (the pending jump survives the full-load fallback, like Checks ↓). Buttons inside a form or dialog are skipped, so the dialog's own submit button is never clicked. |
| Ticket chips | Own row under the nav. IDs come from the PR title and branch name. `AB#123` is treated as ADO; it links once the script has seen any `…/_workitems/edit/…` link on a page (remembered afterwards) or you set `adoBase`. Any other `ABC-123` is Linear. Branch names match case-insensitively; `ticketIgnorePrefixes` filters look-alikes such as `UTF-8` and `fix-12`. Rules live in `ticketRules`. |
| Collapse test and generated files | Finds each file's path from its header (verified against the container's `diff-<sha256>` id) and clicks GitHub's own chevron, so the chevron expands it again. Files you expand stay expanded across refreshes. If no chevron is found, the script hides the body itself and adds a toggle button. Patterns: `generatedPatterns`; tests are `tests/`, `__tests__/`, `*.test.*`, `*.spec.*`, `*_test.py`, `test_*.py`. |
| Dim test files in the tree | Dims test files and folders in the left file tree. Paths are rebuilt from the tree's nested labels, so compacted folders work. |
| Mark files owned by others | CODEOWNERS, last matching rule wins. "Mine" is your login or any `myOwners` team. In the left file tree, files owned by others get an amber dot before the name (hover for the reason). Panel buttons: mark / hide (turn the feature off in settings; hide removes those files from the tree). `minePatterns` (regexes) can mark extra paths as yours. |
| Viewed-state across pushes | Records the file's blob SHA when you tick Viewed (the checkbox, or the newer diff's Viewed button). After a push, files whose SHA differs get a badge, a blue dot in the left file tree (hover for the reason), and are listed in the panel. |
| "Changed since viewed" filter | Adds a **Changed since viewed (N)** checkbox to GitHub's own file tree filter menu, under "Viewed files". It only appears while N > 0. When ticked, the diff and the file tree show only those files (folders with none are hidden), combined with GitHub's own filters. It turns itself off once you've re-viewed them all. The choice is remembered per PR. |
| Next / previous unviewed file | Alt+N jumps to the next file whose Viewed box is unticked, Alt+Shift+N to the previous one. Files collapsed as generated, test, whitespace-only or renamed, and files hidden by a filter, are skipped. Wraps around. Files GitHub hasn't rendered yet are not visible to it. |
| Copy quote with link | Select code in a diff and press Alt+C. Copies a Markdown link to the file and selected lines (`…/files#diff-<id>R10-R12`, `L` for removed lines) followed by the code in a fenced block. If line numbers can't be read it still copies the code with a link to the file. |
| Keyboard shortcut help | Click **?** in the panel bar or press Alt+/ to list every shortcut that is currently enabled. Esc, ✕ or a click outside closes it. |
| Change stats | Additions and deletions by category (source, tests, docs, config, generated). |
| Unresolved thread navigator | Panel buttons, or Alt+J / Alt+K. |
| Hide bot comments | Conversation tab timeline items authored by bots. |
| Snippet expander | Type `;nit` then space in any comment box. Defaults: `;nit`, `;q`, `;block`, `;lgtm`, `;test`, `;why`. Edit via **Edit config (JSON)**. |
| Whitespace hidden by default | Off by default. Redirects to `?w=1` once per tab per PR, and never when the URL already has a `w` parameter. |
| Review progress meter | Top of the panel on every PR tab: a bar plus `62% · 9/14 files · 410/660 lines`. The percentage is weighted by changed lines (additions + deletions). By default generated files and files owned by others (CODEOWNERS, when ownership is on) are left out and listed as "excl. 3 generated, 5 not yours"; **mine / all** switches scope (remembered across PRs). On the Files tab a file's own Viewed control decides. Elsewhere, and for files GitHub hasn't rendered, a file counts as viewed only if the blob SHA recorded when you ticked it matches the current one. The Files tab also brings those records in line with what GitHub shows, so files ticked before installing or on another machine count after one visit to Files. On the Files tab the same figure ("62% of your lines") also sits next to GitHub's own "N / M viewed" counter, even with the panel collapsed; hover it for the file and line counts. |
| Bulk mark viewed | Files tab only. **Mark viewed** buttons for generated, test and not-mine files, each showing how many are still unviewed (hidden at 0). They click GitHub's own Viewed controls, 150ms apart, so GitHub saves the state. Files GitHub hasn't rendered yet have no control; the toast says how many were skipped ("Marked 7 viewed; 3 not loaded yet — scroll down and run again"). |
| Quick file jump | Alt+P on any PR tab opens a file finder. Type part of a name: matching is fuzzy (letters in order), with file-name matches ranked above matches that only work across the whole path. Each row shows +/− counts and the same markers as the tree: blue dot changed since viewed, amber dot owned by others, ✓ viewed, and a generated / test tag. Arrow keys move, Enter jumps, Esc closes. The jump scrolls to the file and expands it if it was collapsed. A file GitHub hasn't rendered yet gets its `#diff-<sha256>` anchor set as the hash, the way the file tree's own links work. From another tab it goes to Files first, and the pending jump survives the full-load fallback like Checks ↓. |
| Suggestion from selection | Select lines on the new side of a diff and press Alt+G. Opens a review comment on those lines (clicks the first line number, shift-clicks the last, then GitHub's "+" button) and puts a ` ```suggestion ` block with the selected lines in it. Whole lines are used even if the selection starts or ends mid-line; diff markers and line numbers are left out; deleted lines are skipped. It never posts the comment. If the comment form doesn't open, the block is copied to the clipboard instead. If GitHub's form doesn't confirm the multi-line range, a toast asks you to check it before posting. Selections that are only deleted lines, or that span hunks, are refused with a toast. |
| Collapse whitespace-only and rename-only files | Pure renames (`similarity index 100%`, no hunks, no mode change) get a **renamed** badge; files where every hunk's old and new text match once all whitespace is removed get **whitespace only** (the same rule as `?w=1`, so re-indents, re-wrapped lines and blank-line or trailing-newline changes count, but moved lines don't). Both collapse like generated files and stay expanded once you expand them. Binary files and mode changes never count. |
| Debug leftovers | Scans added lines (not generated or whitespace-only files) against `leftoverPatterns`: `console.log` / `debugger` / `.only(` in JS/TS, `print(` / `breakpoint()` / `pdb.set_trace(` in Python, `TODO` / `FIXME` anywhere, `localhost` / `127.0.0.1` outside docs, tests and env files. A line is skipped when the same text (ignoring whitespace) was removed in that hunk, so touching an old TODO doesn't flag it. Files get an **N leftovers** badge (hover for the lines) and the panel lists them. Alt+L / Alt+Shift+L (or the list) jumps to the next / previous one: it expands the file if collapsed, scrolls to the line and flashes it. Each pattern is `{ label, pattern, files?, exclude? }` (regex strings; `files` / `exclude` match the path) or a plain regex string. |
| Dependency changes | Panel list of added (+), removed (−) and changed (~) packages per manifest: `package.json` (`dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`), `requirements*.txt` / `requirements*.in`, and `pyproject.toml` (`[project]` dependencies, optional-dependencies, `[dependency-groups]`, build requires, Poetry tables). Lockfiles are ignored. See Maintenance notes for how sections are guessed when a hunk doesn't include its header. |
| Warn before leaving with an unsubmitted review | If your pending review has comments, closing the tab, reloading or following a link off the PR asks first. Same-site links that leave the PR (another PR, issues, a file view) get a `confirm()`; anything else that unloads the page gets the browser's own "Leave site?" prompt. Moving between the PR's own tabs, clicking Submit in the review dialog, and F5 / Ctrl+R don't prompt (the browser's reload button does). A pending review with no comments, or your submitted comments, never count. Browser back/forward inside GitHub's app is not caught, and nor is closing the tab within 10s of clicking a link inside the PR. |
| New commits since your last look | Your last look is the PR's head commit when you last marked a file Viewed. When the head has moved since, the panel shows "N new commits since your last look" with **View changes**, which opens GitHub's own range view (`/pull/<n>/files/<old>..<new>`). After a force-push the old commit isn't in the PR and that view 404s, so it links to `/compare/<old>..<new>` instead and says so. **Dismiss** marks the current head as seen. |

Every feature has a toggle in the settings modal, opened with the ⚙ in the panel bar or Alt+, (grouped, with a Reset to defaults button). **Edit config (JSON)** and **Reset config** are in the Tampermonkey menu; only settings you change are stored.

## Maintenance notes

GitHub's DOM changes. Per-file features anchor on each file container's `id="diff-<sha256 of path>"`, the `data-file-path` button in the header, and the header's chevron button (see `fileEntries`, `fileContainer`, `findChevron`). The file tree is matched through `role="tree"` / `role="treeitem"`. If a per-file feature stops working, those are the first places to look.

The filter row is injected into the React `ActionMenu` that the tree's filter button opens (`[data-component="ActionMenu.Overlay"]`), cloned from its `li[role="menuitemcheckbox"]` whose label is "Viewed files". If GitHub renames that label or restructures the menu, `injectFilterItem` stops adding the row.

Viewed state is read from each file's Viewed control (`VIEWED_CONTROL_SEL`): the classic checkbox, or the newer diff's `button[aria-pressed][aria-label*="viewed"]`. Viewed-state across pushes and Alt+N both depend on it. Alt+C reads line numbers from `[data-line-number]` cells inside the selection's `<tr>` rows (`rowLine`, `selectedRows`), which is verified against the classic diff markup; the newer diff view may fall back to a link without line numbers.

The inline progress chip finds GitHub's counter by its text (`VIEWED_COUNTER`, "3 / 12 viewed" or "3 / 12 files viewed"), not by a selector, and inserts itself after the smallest element whose whole text matches. If GitHub rewords the counter, the chip just doesn't appear.

The progress meter and bulk mark viewed use the same Viewed controls (`viewedControls`, which keeps only the innermost `fileEntries` so a wrapper around several files doesn't borrow the first file's control). The SHA records they read are written by the Viewed listener in `processFile`, which runs while either Viewed-state across pushes or the progress meter is on, and by `syncViewedRecords` on the Files tab. If the meter stops moving when you tick files, check that the listener still binds.

Alt+P jumps through `JUMPS.file`: it finds the target by its `diff-<sha256 of path>` id (or `findFileEl`), and for files that aren't rendered yet sets `location.hash` to that id and waits up to 10s for GitHub to render it. If GitHub stops loading files from the hash, unrendered files will time out with a toast.

Alt+G reads code from the cell after each row's last `[data-line-number]` cell, preferring `.blob-code-inner` (classic) or `.diff-text-inner` (newer view) and otherwise dropping marker elements and buttons (`diffLine`, `codeText`). It opens the comment by dispatching clicks on the line-number cells (shift-click for the range), a simulated hover on the last row, then clicking `button.js-add-line-comment` or any row button whose aria-label mentions "comment" (`COMMENT_BUTTON_SEL`, `openLineComment`). It checks the multi-line range against the form's "lines N to M" text (`COMMENT_RANGE`). The code extraction is checked against classic markup; opening the comment form, in either view, has not been checked against a live page.

Debug leftover jumps find the line by the classic diff's cell id `<file id>R<line>`, then fall back to a `<tr>` whose last `[data-line-number]` is that new-side line (`findLineRow`). If the file isn't rendered at all, the script sets `location.hash` to `#<file id>R<line>` and waits up to 3s for GitHub to load it; off the Files tab, panel links go to Files with that hash. Lines in a diff GitHub hasn't loaded ("Load diff") or in rows the newer view hasn't rendered can't be reached; the script scrolls to the file and says so. Leftover patterns are applied while the diff is parsed, so editing `leftoverPatterns` re-fetches the diff.

Dependency sections are tracked per side (old/new) from header lines seen in each hunk (`"devDependencies": {`, `[tool.poetry.dependencies]`, `dependencies = [`) and from git's hunk-header context, which for TOML is often the enclosing `key = [` line. When a hunk starts inside a section without showing its header, entries are guessed by shape: in `package.json`, a `"name": "<version-like>"` line indented two levels or more (excluding `version`, `node`, `npm` and similar); in `pyproject.toml`, a quoted requirement with a version operator, or a `name = "^1.2"`-style Poetry line. Unchanged context lines only update the section state; a package that appears with the same version on both sides is not listed unless it moved between known sections.

The pending-review warning reads the count from GitHub's own review button: in the React Files view, the `[data-component="ButtonCounter"]` inside `button[class*="ReviewMenuButton__"]` (Primer's `count` prop, set to the number of pending comments); in the classic view, `.js-pending-review-comment-count`. On a fresh load it also reads `viewerPendingReview` from the React payload (`react-app[initial-path]` → `script[data-target="react-app.embeddedData"]`), used only when that payload was rendered for the current PR. The last count seen sticks while you're on a tab without the button. Submitting from the React dialog sets `location.href` before the count re-renders, so beforeunload stays quiet while `#anchored-review-title` (the review overlay's heading) is on the page. See `livePendingCount`, `payloadPendingCount` and `reviewDialogOpen`.

"New commits since your last look" reads `payload.pullRequestsCommitsRoute.commitGroups[].commits[].oid` from the commits route (with a fallback that parses the same payload out of the HTML page) and cross-checks the last commit against the SHA embedded in `metadata.commitHeadShaChannel`. If the route is truncated or the two disagree, the feature shows nothing. `.patch` isn't used because it leaves out merge commits, so its last commit isn't the head after a "Merge main into …" push. See `parseCommitOids`.

Not built: ticket hover cards, per-file private notes, lockfile dependency parsing.
